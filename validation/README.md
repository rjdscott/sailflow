# `validation/`

The harness that says whether the solver is any good. It only ever **reads**:
calibration is fitted in `calibration/` and frozen into `data/boats/j70.json`;
nothing here writes a knob (ADR 0007).

## Files

| File | What it is |
|------|------------|
| `compare.ts` | Shared plumbing: boat + polar loading, the ADR 0007 tolerances, the ADR 0012 row set (`gateRows()`), the boat/calibration hashes, and `compareRow()` — one polar row replayed through the solver. |
| `invariants.test.ts` | The eighteen solver invariants (18 `describe` blocks, 58 assertions). Statements about signs, symmetry and monotonicity, never magnitudes, so they hold both before and after calibration. |
| `polar.test.ts` | The hold-out gate. Currently **fails** on the known held-out rows listed under "Where the model is honestly weak" in `ASSUMPTIONS.md` — the TWS 14 upwind VMG row misses the 3 % tolerance by 2.8 points. That is a real model deficiency on record, not a missing calibration. |
| `golden.test.ts` | Replays `golden/*.json` and asserts nothing moved. |
| `report.ts` | Writes `report.md`: polar comparison, gate verdict, model-vs-guide dock settings, honest weaknesses. |
| `golden/` | The golden corpus, generated by `pnpm golden` (owned by `calibration/`). |
| `report.md` | Generated. Not linted, not hand-edited. |

## Running

```bash
pnpm vitest run validation/invariants                  # ~2 s, 58 tests
pnpm vitest run validation/golden                      # ~1 s, 3 files; skips only when the corpus is empty
pnpm vitest run validation                             # ~2 s, 61 tests — invariants + golden, NOT the gate
pnpm vitest run --config vitest.polar.config.ts        # ~1 s, 5 tests, the gate
pnpm tsx validation/report.ts                          # ~12 s, writes validation/report.md
pnpm validate                                          # the gate, then the report; exits on the gate's status
```

`validation/polar.test.ts` is **excluded** from the default vitest config
(`vite.config.ts`), so `pnpm vitest run validation/polar` matches no files and
runs nothing. The gate has its own config, `vitest.polar.config.ts`, which is
what `pnpm validate` and the CI `validate` job use.

## What the gate means

ADR 0007 splits calibration from validation and freezes the tolerances; ADR
0012 supersedes its split, dividing by wind speed instead of by angle. Hydro
and rig/shape parameters are fitted on **every printed row at TWS 6, 10, 12,
16 and 20**. The gate is defined on what the fit never saw — **every row at
TWS 8 and 14** (`gateRows()` in `compare.ts`, 10 rows):

- **VMG rows** (jib upwind, asymmetric downwind): boat speed within **3 %**,
  VMG angle within **2°**.
- **60°, 90° and 120° rows at those two wind speeds**: boat speed within
  **5 %** (tier B).

The 60/90/120° rows at the *fitted* wind speeds are not gated. ADR 0007 held
them out at every TWS; ADR 0012 folded them into the fit, so their residuals
are fit residuals and `validation/report.md` labels them as such. A pass means
the model generalises. A fit residual would mean only that the optimiser
worked. **Do not loosen a tolerance to make the gate green** — changing one
requires superseding ADR 0007.

`validation/report.md` displays all 25 printed rows with a FIT/HELD-OUT label
per wind speed, and computes its verdict over the same `gateRows()` set the
vitest gate uses, so the shipped report and `pnpm validate` cannot disagree.

Two conventions the ORC Speed Guide does not print, and which calibration must
share with the gate or the two disagree for no reason. Both are exported from
`compare.ts`:

```ts
POLAR_SEA_STATE = 1   // ripple; an ORC VPP polar always carries some wave drag
POLAR_CREW_KG         // boat.crew.maxKg — class-max crew, hiking hard
```

The polar prints fixed-angle rows for the **jib** table only (the asymmetric
table prints its VMG row alone), so the 60/90/120° rows are all jib rows and
are solved as such.

## Golden corpus format

`golden.test.ts` reads every `golden/*.json`. One file:

```json
{
  "boatHash": "3e0f6256",
  "calibHash": "319cc81d",
  "cases": [
    {
      "id": "upwind-10kt",
      "call": "trimmed",
      "controls": { "dock": { "upperTurns": 0, "lowerTurns": 0, "forestayMm": 0 }, "race": { "...": 0 } },
      "condition": { "twsKt": 10, "twaDeg": 42, "seaState": 1, "crewKg": 320, "sailset": "jib" },
      "result": { "...": "the SolveResult, JSON round-tripped" }
    },
    {
      "id": "vmg-up-12kt",
      "call": "optimal",
      "dock": { "upperTurns": 0, "lowerTurns": 0, "forestayMm": 0 },
      "opts": { "optimiseTwa": true },
      "condition": { "twsKt": 12, "twaDeg": 45, "seaState": 1, "crewKg": 320, "sailset": "jib" },
      "result": { "...": "the OptimalResult, JSON round-tripped" }
    }
  ]
}
```

- `boatHash` / `calibHash` come from `boatHash()` / `calibHash()` in
  `compare.ts`. Both are optional, and a stale one is treated differently:
  - a stale **`calibHash`** **skips** the file with "run `pnpm golden`". A
    recalibration is a deliberate re-fit of every knob, so every number in
    the corpus is expected to move and a skip is not hiding anything.
  - a stale **`boatHash`** (with `calibHash` current) **fails**, naming
    `pnpm golden` in the message. A geometry or boat-file edit is not a
    recalibration: it is exactly the class of change the corpus exists to
    catch. Skipping one turned the regression net off silently from #79
    (which added `baseRaceDown` to `data/boats/j70.json` without
    regenerating) through #80's kite-geometry change, while `make check`
    stayed green and proved nothing about solver stability.

  So: change the boat file deliberately, confirm the diff to the corpus is
  the change you meant, then run `pnpm golden` and commit it in the same PR.
- Numbers must match within **1e-6 relative**; strings and booleans exactly.
- An empty `golden/` skips the whole suite.
